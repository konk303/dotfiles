# セルフコードレビュー（敵対的検証）

現在のブランチの変更内容を、複数のサブエージェントで敵対的にレビューし、挙がった指摘を反証にかけて確度の高いものだけを残します。

**⚠️ planモードでは実行しないこと**

## 実行手順

### 1. 事前情報の収集

現在のブランチと、ベースブランチ（`develop`）との差分を取る。

```bash
git branch --show-current
git diff --name-only develop...HEAD
git diff develop...HEAD
```

ベースブランチが `develop` でないリポジトリでは、`main` など実際のベースに読み替える。

### 2. 観点の選定

変更内容に応じて 3〜5 個の観点を選ぶ。全観点を機械的に流すと、無関係な観点のエージェントが空振りする。

**サーバサイド（モデル・コントローラ・ジョブ）の変更**
- セキュリティ: SQLインジェクション、XSS、CSRF、認証・認可、機密情報のハードコード
- パフォーマンス: N+1、不要なクエリ、メモリ効率、インデックス
- Rails規約: Strong Parameters、コールバック、スコープ、バリデーション
- コード品質: 実在しない共通の抽象化、命名、責務、エラーハンドリング、実装漏れ
- テスト: カバレッジ、エッジケース、テストが本当に壊れを検知するか

**フロントエンド（view・JS・CSS）の変更**
- 挙動・エッジケース: 読み込み順序、JS の失敗時、ブラウザの戻る/進む（bfcache）、複数タブ、ストレージ不可の環境、CSP
- レイアウト・CSS: 詳細度とレイヤー順、ルートの font-size を踏まえた実寸、レスポンシブ、印刷、スクロール位置
- 既存機能への干渉・アクセシビリティ: 既存の JS コンポーネント、キーボード操作、フォーカス、aria、既存テストが素通りしないか

### 3. 並列レビュー実行 ⚠️ 必須: Agent（Task）ツール使用

**必ず Agent ツール（環境によっては Task）を使って並列実行すること。直接実行してはいけない。**
選んだ観点ごとに Agent を1つ立て、**1つのメッセージ内で同時に呼び出す**（並列実行のため）。
`subagent_type: "general-purpose"` を使う（実際に grep・ビルド・テストを走らせて裏を取らせるため。`Explore` は抜粋を読むだけなので実測しない）。

**全エージェントのプロンプト冒頭に必ず入れる共通スタンス:**

```
あなたは敵対的レビュアーです。この実装は壊れているという前提で、実際に壊れる条件を見つけてください。
・「問題なさそう」で終わらせず、必ず具体的な再現条件を示すこと
・根拠はファイル名と行番号で示すこと（推測で書かない。実際にファイルを読む）
・数値は実測または計算すること（「小さい」ではなく「実測 21×21px」）
・問題なしと判断した項目も、なぜ問題ないかの根拠を1行で列挙すること
・必要ならコマンドを実行して確認してよい（テストコマンドは下記「テストの実行方法」を参照）

出力: 「重大度（高/中/低）・再現条件・根拠のファイルと行・修正案」の形で列挙。
```

各エージェントには、その観点で見るべき具体的な項目を3〜6個、箇条書きで渡す（漠然と「チェックして」と渡さない）。

### 4. 指摘の反証 ⚠️ 必須: Agent（Task）ツール使用

ステップ3で挙がった指摘のうち、**重大度が高・中のものそれぞれ**に、独立した反証エージェントを1体立てる（並列、`subagent_type: "general-purpose"`）。

```
次の指摘を反証してください: {指摘の内容と根拠}

・誤りである根拠、または実際には発生しない条件を探すこと
・前提が成り立っているかを実際のコードで確かめること
・判断に迷う場合は refuted=true（偽陽性として捨てる）に倒すこと

出力: refuted（true/false）と、その判断の根拠（ファイルと行）。
```

反証されなかった指摘だけを次のステップに残す。反証で消えた指摘は、最終報告に「偽陽性として除外」として1行だけ残す（何を検討したかが分かるように）。

### 5. レビュー結果の統合

```markdown
## コードレビュー結果

### 🔴 要修正（Critical）
- **{指摘}**
  - 再現条件: {具体的な操作・環境}
  - 根拠: `path/to/file.rb:12`
  - 修正案: {案}

### 🟡 推奨修正（Warning）
（同じ形式）

### 🟢 提案（Suggestion）
（同じ形式）

### ⚪ 偽陽性として除外
- {指摘}（理由: {1行}）

### ✅ 良い点
```


## 注意事項

- 変更されたファイルのみをレビュー対象とする
- 既存コードの問題は指摘しない（今回の変更に関係するもののみ）
- 過度に細かい指摘は避ける
- レビュー結果は会話で出す。GitHub には投稿しない（bot 宛の返信は別）
- **サブエージェントの報告を鵜呑みにしない**。前提が間違っていることがあるため、重要な指摘は自分でもファイルを開いて確かめる
- 簡易な実装でも 30 分程度かかることがある
