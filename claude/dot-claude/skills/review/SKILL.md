# コードレビュー（検証優先）

指摘は仮説、検証が判定。変更の意図を先に言葉にし、実際に動かして確かめ、そのうえで「意図を壊す具体的な条件」を探します。残すのは裏が取れた指摘だけで、指摘が0件で終わるのは正常な結果です。

- 引数なし: 現在のブランチの変更をレビューする（セルフレビュー）
- 引数に PR の URL（`/review https://github.com/owner/repo/pull/123`）: その PR をレビューする（PR モード）。他人の PR なので修正はせず、最後に投稿用の結果を出す
- 引数に Slack のスレッドの URL（`/review https://….slack.com/archives/C…/p…`）: そのスレッドで頼まれた SQL をレビューする（SQL モード）。修正はせず、最後に返信用の結果を出す

今回の引数: `$ARGUMENTS`（空ならセルフレビュー）

**⚠️ planモードでは実行しないこと**

## 指摘として扱うもの・扱わないもの

**扱う**: この変更によって、意図した挙動または既存の挙動が壊れる具体的な条件（入力・操作・データの状態）を示せるもの。バグ、データの破損、セキュリティ上の穴、実測できる性能の劣化、壊れを検知できないテスト。

**扱わない**（レビュアーにも渡さず、挙がっても捨てる）:
- 命名、コメントの文言、書式、構造の好み
- 「将来〜になるかもしれない」という先取りの提案（抽象化、拡張性、汎用化）
- 壊れる条件を示せない「〜の恐れがある」「〜すべき」
- カバレッジの数字そのもの（壊れを見逃す具体的なケースを示せるなら扱う）
- 公式ドキュメントの「推奨」に沿っていないだけで、実際には動くもの
- 今回の変更に関係しない既存コードの問題

## 実行手順

### 1. 事前情報の収集と、意図の言語化

```bash
# ブランチ名を取得
git branch --show-current

# コミット済みの変更 developブランチと比較
git diff --name-only develop...HEAD
git diff develop...HEAD

# 未コミットの変更も対象に含める（コミット前にレビューをかけることが多い）
git status --short
git diff
git diff --staged
```

ベースブランチが `develop` でないリポジトリでは、`main` など実際のベースに読み替える。

**重要**: `git diff develop...HEAD` が空でも、作業ツリーに変更があればそれがレビュー対象。差分が空だからといってレビューを終わらせない。

**PR モード**（引数に PR の URL があるとき）は、上の代わりに次で集める。ローカルの作業ツリーは切り替えない（`gh pr checkout` はしない）。

```bash
gh pr view <URL> --json number,title,body,baseRefName,headRefName,headRefOid,files
gh pr diff <URL>
```

変更後のファイル全体を読む必要があるときは、`gh api "repos/{owner}/{repo}/contents/{path}?ref={headRefOid}" --jq .content | base64 -d` で読む。

**SQL モード**（引数に Slack のスレッドの URL があるとき）は、次で集める。

- URL の `archives/<チャンネルID>/p<数字>` から、チャンネル ID と親メッセージの ts（数字の後ろから6桁の前に `.` を入れたもの）を取り、Slack の `slack_read_thread` でスレッドを読む。`?thread_ts=` があればそれが親の ts
- スレッドの依頼文から、レビューする SQL・目的・期限・関連リンク（元の依頼、Notion など）を読む。リンク先も読む
- 対象のシステムのリポジトリが手元にあれば、スキーマ（`db/Schemafile` や `db/schema.rb`）とモデルを読み、テーブル・カラム・外部キー・論理削除の扱いを確かめる

**意図の言語化**: 集めた情報（会話、コミットメッセージ、PR 本文、依頼文）から、この変更が「何をどう変えるものか」「何は変えないはずか」を2〜4行で書く。以降の指摘はすべて、この意図か既存の挙動を壊すかどうかで判定する。意図が読み取れないときは、推測で進めずユーザーに聞く。

### 2. まず動かして確かめる

レビューの前に、変更を実際に動かす。ここで見つかった失敗は、そのまま裏の取れた指摘になる。

- **セルフレビュー**: 変更に関係するテストと Lint を実行する（実行方法はリポジトリの README や CLAUDE.md に従う）。テストで覆われていない挙動は、意図した入力で実際に動かす（コンソール、スクリプト、画面なら実際に操作）。境界になりそうな入力（空、NULL、0件、月末・日付の境目、権限の無いユーザーなど、この変更に関係するもの）を1〜3個選んで試す
- **PR モード**: CI の結果を `gh pr checks <URL>` で見る。手元で動かすと確かめられる疑問があれば、`git worktree add` で PR の head を別のディレクトリに取り出して動かす（今の作業ツリーは切り替えない）。終わったら worktree を消す
- **SQL モード**: 本番では実行しない。手元の DB があれば、対象を数える SELECT に書き換えて実行する。無ければスキーマとモデルから追う

実行したコマンドと結果は、次のステップでレビュアーに渡す。

### 3. 観点の選定

変更の大きさと内容に応じて **1〜3 個**の観点を選ぶ。小さな変更（数十行、1つの関心事）なら1個でよい。全観点を機械的に流すと、無関係な観点のエージェントが無理に指摘を作る。

**サーバサイド（モデル・コントローラ・ジョブ）の変更**
- 正しさ: 意図どおりの結果になるか、境界値、NULL、並行実行、エラー時の状態、実装漏れ
- セキュリティ: SQLインジェクション、XSS、CSRF、認証・認可、機密情報のハードコード
- パフォーマンス: N+1、不要なクエリ、インデックス（発行されるクエリや件数を実測できるものに限る）
- テスト: 今回の変更を壊してもテストが通ってしまわないか

**フロントエンド（view・JS・CSS）の変更**
- 挙動・エッジケース: 読み込み順序、JS の失敗時、ブラウザの戻る/進む（bfcache）、複数タブ、ストレージ不可の環境、CSP
- レイアウト・CSS: 詳細度とレイヤー順、ルートの font-size を踏まえた実寸、レスポンシブ、印刷、スクロール位置
- 既存機能への干渉・アクセシビリティ: 既存の JS コンポーネント、キーボード操作、フォーカス、aria、既存テストが素通りしないか

**SQL（SQL モードでは必ず選ぶ）**
- 対象の絞り込み: WHERE・JOIN の条件で、意図した行だけが対象になるか（NULL、論理削除、重複、型の違い）
- 安全性: トランザクションで囲んでいるか、実行前後の確認クエリと期待値があるか、戻す手順があるか、本番での実行順
- 影響範囲: 外部キーや参照している他のテーブル、アプリのコールバックを通らない更新で崩れる整合性
- 性能: 対象の件数、ロックの範囲と時間、インデックスが効くか

**公式ドキュメントとの食い違い**（設定ファイルや外部の仕組みの書き方そのものが変更の中心のときだけ選ぶ）
- 対象と参照先の例: Claude Code の CLAUDE.md・`.claude/rules/`・settings・skills・hooks → https://code.claude.com/docs/llms.txt から該当ページ／GitHub Actions・Dependabot → docs.github.com／Rails → guides.rubyonrails.org
- 見ること: 書いた設定・呼び出しが、公式の仕様どおりに動くか（存在しないキー、廃止された書き方、仕様と違う前提）。「推奨と違う」だけでは指摘にしない
- 公式ドキュメントは WebFetch で実際に読み、指摘には参照したページの URL と該当箇所を付ける（記憶で書かない）

### 4. 並列レビュー実行 ⚠️ 必須: Agentツール使用

選んだ観点ごとにエージェントを1つ立て、**1つのメッセージ内で同時に呼び出す**（並列実行のため）。
`subagent_type: "general-purpose"` を使う（実際に grep・ビルド・テストを走らせて裏を取らせるため。`Explore` は抜粋を読むだけなので実測しない）。

各エージェントには、次を渡す: ステップ1の意図、差分の取り方（または差分そのもの）、ステップ2で実行したコマンドと結果、その観点で見るべき具体的な項目を3〜6個（漠然と「チェックして」と渡さない）。

**全エージェントのプロンプト冒頭に必ず入れる共通スタンス:**

```
あなたはこの変更のレビュアーです。この変更が、下に書いた意図または既存の挙動を壊す具体的な条件を探してください。

・指摘は、できる限り実行して裏を取ること（失敗するテスト、再現スクリプト、誤った結果を示すコマンドの出力）。実行したコマンドと出力をそのまま付ける
・実行できないもの（本番データ、外部サービスなど）は、具体的な入力からコードをたどり、どの行でどう誤った結果になるかをファイル名と行番号で示すこと
・どちらもできない指摘は報告しない。「〜の恐れがある」「〜すべき」で終わるものは不要
・次は報告しない: 命名、コメントの文言、書式、構造の好み、「将来必要になるかもしれない」提案、今回の変更に関係しない既存コードの問題
・数値は実測または計算すること（「小さい」ではなく「実測 21×21px」）
・指摘が0件でもよい。無理に探して作らないこと。0件のときは、何を実行して・何を読んで確かめたかを2〜3行で書く
・試すためのファイルは作業ツリーに残さない（スクラッチ用のディレクトリを使うか、終わったら消す）

出力: 指摘ごとに「何が壊れるか（1行）・再現条件・裏付け（実行したコマンドと出力／たどった入力とファイル:行）・裏付けの種類（実行／追跡）・修正案」。
```

### 5. 指摘の検証

挙がった指摘を、裏付けの種類で分けて確かめる。

- **実行で裏を取った指摘**: 付いているコマンドを自分で実行し直す。同じ失敗が出て、それが意図か既存の挙動を壊しているなら残す。再現しなければ捨てる
- **追跡で裏を取った指摘**: 実行に置き換えられないか、まず自分で試す（置き換えられたら上の扱い）。置き換えられないものは、指摘ごとに独立した反証エージェントを1体立てる（並列、`subagent_type: "general-purpose"`）

```
次の指摘を反証してください: {指摘の内容と裏付け}

・誤りである根拠、または実際には発生しない条件を探すこと
・前提が成り立っているかを実際のコードで確かめること。実行して確かめられるなら実行すること
・判断に迷う場合は refuted=true（偽陽性として捨てる）に倒すこと

出力: refuted（true/false）と、その判断の根拠（ファイルと行、または実行したコマンドと出力）。
```

同じ原因の指摘は1つにまとめる。「扱わないもの」に当たる指摘は、反証にかけずにここで捨てる。捨てた指摘は、最終報告に1行だけ残す（何を検討したかが分かるように）。

### 6. レビュー結果の統合

```markdown
## コードレビュー結果

### 意図
{ステップ1で書いた意図}

### 確かめたこと
- {実行したテスト・操作と結果}

### 🔴 要修正（実行で確認済み）
- **{指摘}**
  - 再現条件: {具体的な操作・環境}
  - 裏付け: {コマンドと出力の要点}
  - 修正案: {案}

### 🟡 要確認（実行では確かめられなかったが、反証されなかった）
- **{指摘}**
  - 再現条件: {具体的な入力・状態}
  - 根拠: `path/to/file.rb:12`
  - 修正案: {案}

### ⚪ 除外
- {指摘}（理由: {1行}）
```

指摘が無い区分は「なし」と書く。両方とも「なし」なら、それが結論。指摘を埋めるために基準を下げない。

**PR モード**では、上の結果に続けて、PR に投稿するコメントの案を次の形で最後に出す。投稿はしない（ユーザーが確かめてから投稿する）。

```markdown
#### 全体のコメント
{確かめたことと、要修正・要確認の要約。指摘が無ければその旨と、確かめた内容}

#### 行コメント
- `app/models/foo.rb:12` 🔴 要修正: …／再現条件: …／修正案: …
```

- 行コメントには検証で残った指摘だけを入れる。除外したものは入れない
- 行番号は変更後のファイルの行番号（diff の `+` 側）。差分に含まれない行への指摘は、全体のコメントに回す
- 本文は日本語で、再現条件・修正案を書く。要確認の指摘は、断定せず質問の形で書く

**SQL モード**では、上の結果に続けて、Slack のスレッドに返信する文の案を最後に出す。返信はしない（ユーザーが確かめてから返信する）。

- 要修正・要確認を箇条書きで書き、問題が無ければ :lgtm: を付ける
- 返信は依頼した人が読む前提で、日本語で短く書く。検証で残った指摘だけを入れる

### 7. 問題の修正（PR モード・SQL モードではしない）

- **要修正**: 直す。できるときは、先に失敗するテスト（または再現コマンド）を用意し、修正後に通ることを確かめる
- **要確認**: 自動では直さない。結果に載せてユーザーの判断を待つ
- レビュー中に気づいた typo など明らかな誤りは、指摘に数えずその場で直してよい

修正後は、ステップ2で実行したテストと Lint をもう一度実行して通ることを確かめる。修正した箇所に対してレビューをやり直すのは、修正がロジックを大きく変えたときだけ。

### 8. レビュー結果をファイルに保存（PR モード・SQL モードではしない）

```bash
mkdir -p tmp/claude/review/{ブランチ名}
```

ファイル: `tmp/claude/review/{ブランチ名}/review_result.md`

保存後、Emacs で開く（`$EDITOR` は emacsclient）:
```bash
emacsclient -n tmp/claude/review/{ブランチ名}/review_result.md
```

## 注意事項

- 変更されたファイルのみをレビュー対象とする
- レビュー結果は会話で出す。このコマンドは GitHub にも Slack にも投稿しない（PR モード・SQL モードも案を出すだけで、投稿はユーザーが行う）
- **サブエージェントの報告を鵜呑みにしない**。前提が間違っていることがあるため、残す指摘は自分でも再実行するかファイルを開いて確かめる
