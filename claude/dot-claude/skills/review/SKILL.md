# セルフコードレビュー（敵対的検証）

変更内容を、複数のサブエージェントで敵対的にレビューし、挙がった指摘を反証にかけて確度の高いものだけを残します。

- 引数なし: 現在のブランチの変更をレビューする（セルフレビュー）
- 引数に PR の URL（`/review https://github.com/owner/repo/pull/123`）: その PR をレビューする（PR モード）。他人の PR なので修正はせず、最後に投稿用の結果を出す
- 引数に Slack のスレッドの URL（`/review https://….slack.com/archives/C…/p…`）: そのスレッドで頼まれた SQL をレビューする（SQL モード）。修正はせず、最後に返信用の結果を出す

今回の引数: `$ARGUMENTS`（空ならセルフレビュー）

**⚠️ planモードでは実行しないこと**

## 実行手順

### 1. 事前情報の収集

```bash
# ブランチ名を取得
git branch --show-current

# コミット済みの変更 developブランチと比較
git diff --name-only develop...HEAD
git diff develop...HEAD

# 未コミットの変更も対象に含める（コミット前にレビューをかけることが多い）
git status --short
git diff
git diff --staged
```

ベースブランチが `develop` でないリポジトリでは、`main` など実際のベースに読み替える。

**重要**: `git diff develop...HEAD` が空でも、作業ツリーに変更があればそれがレビュー対象。差分が空だからといってレビューを終わらせない。

**PR モード**（引数に PR の URL があるとき）は、上の代わりに次で集める。ローカルの作業ツリーは切り替えない（`gh pr checkout` はしない）。

```bash
gh pr view <URL> --json number,title,body,baseRefName,headRefName,headRefOid,files
gh pr diff <URL>
```

変更後のファイル全体を読む必要があるときは、`gh api "repos/{owner}/{repo}/contents/{path}?ref={headRefOid}" --jq .content | base64 -d` で読む。

**SQL モード**（引数に Slack のスレッドの URL があるとき）は、次で集める。

- URL の `archives/<チャンネルID>/p<数字>` から、チャンネル ID と親メッセージの ts（数字の後ろから6桁の前に `.` を入れたもの）を取り、Slack の `slack_read_thread` でスレッドを読む。`?thread_ts=` があればそれが親の ts
- スレッドの依頼文から、レビューする SQL・目的・期限・関連リンク（元の依頼、Notion など）を読む。リンク先も読む
- 対象のシステムのリポジトリが手元にあれば、スキーマ（`db/Schemafile` や `db/schema.rb`）とモデルを読み、テーブル・カラム・外部キー・論理削除の扱いを確かめる

### 2. 観点の選定

変更内容に応じて 3〜5 個の観点を選ぶ。全観点を機械的に流すと、無関係な観点のエージェントが空振りする。

**サーバサイド（モデル・コントローラ・ジョブ）の変更**
- セキュリティ: SQLインジェクション、XSS、CSRF、認証・認可、機密情報のハードコード
- パフォーマンス: N+1、不要なクエリ、メモリ効率、インデックス
- Rails規約: Strong Parameters、コールバック、スコープ、バリデーション
- コード品質: 実在しない共通の抽象化、命名、責務、エラーハンドリング、実装漏れ
- テスト: カバレッジ、エッジケース、テストが本当に壊れを検知するか

**フロントエンド（view・JS・CSS）の変更**
- 挙動・エッジケース: 読み込み順序、JS の失敗時、ブラウザの戻る/進む（bfcache）、複数タブ、ストレージ不可の環境、CSP
- レイアウト・CSS: 詳細度とレイヤー順、ルートの font-size を踏まえた実寸、レスポンシブ、印刷、スクロール位置
- 既存機能への干渉・アクセシビリティ: 既存の JS コンポーネント、キーボード操作、フォーカス、aria、既存テストが素通りしないか

**SQL（SQL モードでは必ず選ぶ）**
- 対象の絞り込み: WHERE・JOIN の条件で、意図した行だけが対象になるか（NULL、論理削除、重複、型の違い）
- 安全性: トランザクションで囲んでいるか、実行前後の確認クエリと期待値があるか、戻す手順があるか、本番での実行順
- 影響範囲: 外部キーや参照している他のテーブル、アプリのコールバックを通らない更新で崩れる整合性
- 性能: 対象の件数、ロックの範囲と時間、インデックスが効くか

**公式のベストプラクティス**（変更対象に公式ドキュメントがあるときは必ず選ぶ）
- 対象と参照先の例: Claude Code の CLAUDE.md・`.claude/rules/`・settings・skills・hooks → https://code.claude.com/docs/llms.txt から該当ページ／GitHub Actions・Dependabot → docs.github.com／Rails → guides.rubyonrails.org
- 見ること: 公式の推奨に沿っているか、非推奨・廃止の書き方をしていないか、公式が勧める確認方法で動作を確かめているか（PR 本文・テスト・手順に確認方法が書かれているか）
- 公式ドキュメントは WebFetch で実際に読み、指摘には参照したページの URL と該当箇所を付ける（記憶で書かない）

### 3. 並列レビュー実行 ⚠️ 必須: Agentツール使用

**必ずAgentツールを使って並列実行すること。直接実行してはいけない。**
選んだ観点ごとにエージェントを1つ立て、**1つのメッセージ内で同時に呼び出す**（並列実行のため）。
`subagent_type: "general-purpose"` を使う（実際に grep・ビルド・テストを走らせて裏を取らせるため。`Explore` は抜粋を読むだけなので実測しない）。

**全エージェントのプロンプト冒頭に必ず入れる共通スタンス:**

```
あなたは敵対的レビュアーです。この実装は壊れているという前提で、実際に壊れる条件を見つけてください。
・「問題なさそう」で終わらせず、必ず具体的な再現条件を示すこと
・根拠はファイル名と行番号で示すこと（推測で書かない。実際にファイルを読む）
・数値は実測または計算すること（「小さい」ではなく「実測 21×21px」）
・問題なしと判断した項目も、なぜ問題ないかの根拠を1行で列挙すること
・必要ならコマンドを実行して確認してよい（テストの実行方法はリポジトリの README や CLAUDE.md に従う）

出力: 「重大度（高/中/低）・再現条件・根拠のファイルと行・修正案」の形で列挙。
```

各エージェントには、その観点で見るべき具体的な項目を3〜6個、箇条書きで渡す（漠然と「チェックして」と渡さない）。

### 4. 指摘の反証 ⚠️ 必須: Agentツール使用

ステップ3で挙がった指摘のうち、**重大度が高・中のものそれぞれ**に、独立した反証エージェントを1体立てる（並列、`subagent_type: "general-purpose"`）。

```
次の指摘を反証してください: {指摘の内容と根拠}

・誤りである根拠、または実際には発生しない条件を探すこと
・前提が成り立っているかを実際のコードで確かめること
・判断に迷う場合は refuted=true（偽陽性として捨てる）に倒すこと

出力: refuted（true/false）と、その判断の根拠（ファイルと行）。
```

反証されなかった指摘だけを次のステップに残す。反証で消えた指摘は、最終報告に「偽陽性として除外」として1行だけ残す（何を検討したかが分かるように）。

### 5. レビュー結果の統合

```markdown
## コードレビュー結果

### 🔴 要修正（Critical）
- **{指摘}**
  - 再現条件: {具体的な操作・環境}
  - 根拠: `path/to/file.rb:12`
  - 修正案: {案}

### 🟡 推奨修正（Warning）
（同じ形式）

### 🟢 提案（Suggestion）
（同じ形式）

### ⚪ 偽陽性として除外
- {指摘}（理由: {1行}）

### ✅ 良い点
```

**PR モード**では、上の結果に続けて、PR に投稿するコメントの案を次の形で最後に出す。投稿はしない（ユーザーが確かめてから投稿する）。

```markdown
#### 全体のコメント
{良い点と、要修正・推奨修正の要約}

#### 行コメント
- `app/models/foo.rb:12` 🔴 要修正: …／再現条件: …／修正案: …
```

- 行コメントには反証で残った指摘だけを入れる。偽陽性として除外したものは入れない
- 行番号は変更後のファイルの行番号（diff の `+` 側）。差分に含まれない行への指摘は、全体のコメントに回す
- 本文は日本語で、重大度・再現条件・修正案を書く

**SQL モード**では、上の結果に続けて、Slack のスレッドに返信する文の案を最後に出す。返信はしない（ユーザーが確かめてから返信する）。

- 要修正・推奨修正・提案を箇条書きで書き、問題が無ければ :lgtm: を付ける
- 返信は依頼した人が読む前提で、日本語で短く書く。反証で残った指摘だけを入れる

### 6. 問題の自動修正（PR モード・SQL モードではしない）

深刻度に関わらず、すべての問題に対して自動修正を試みる:

1. 軽微な問題（typo、空行、インデント等）→ 即座に自動修正
2. 重大な問題（ロジック、セキュリティ、N+1等）→ 自動修正を試みる
3. **自動修正できない場合のみ**停止してユーザーに報告する

修正後は、テストと Lint を実行して通ることを確かめる。

### 7. レビュー結果をファイルに保存（PR モード・SQL モードではしない）

```bash
mkdir -p tmp/claude/review/{ブランチ名}
```

ファイル: `tmp/claude/review/{ブランチ名}/review_result.md`

保存後、VSCodeで開く:
```bash
code tmp/claude/review/{ブランチ名}/review_result.md
```

## 注意事項

- 変更されたファイルのみをレビュー対象とする
- 既存コードの問題は指摘しない（今回の変更に関係するもののみ）
- 過度に細かい指摘は避ける
- レビュー結果は会話で出す。このコマンドは GitHub にも Slack にも投稿しない（PR モード・SQL モードも案を出すだけで、投稿はユーザーが行う）
- **サブエージェントの報告を鵜呑みにしない**。前提が間違っていることがあるため、重要な指摘は自分でもファイルを開いて確かめる
